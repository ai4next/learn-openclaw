# s01: 代理循环


> **"循环是神圣的。永远不要改变它。围绕它分层构建机制。"**
>
> Harness 层：核心循环

## 问题

如何构建一个能够进行对话、响应请求并知道何时停止的代理——而无需硬编码每一种可能的流程？大多数简单的实现将 LLM 调用视为一次性操作：发送提示，得到结果，结束。但真正的代理需要处理多轮推理、工具使用和条件性继续，所有这些都基于同一个简单的核心。

答案是使用由模型自身的 `stop_reason` 信号驱动的 `while True` 循环。由模型决定本轮是否结束，而不是由 harness 决定。

## 解决方案

```
                +-----------+     +-----------+
                |  代理     |     |  模型     |
+-----------+   |  循环     |     |  (LLM)    |
|  用户     |-->|  while    |-->|           |
|  输入     |   |  True     |     |           |
+-----------+   +-----------+     +-----------+
                      |                 |
                      |          +-----------+
                      |          |  stop_    |
                      |          |  reason?  |
                      |          +-----------+
                      |           |         |
                      |       end_turn   continue
                      |           |         |
                      |        +-----+   +-----+
                      |        | 发送|   | 循环|
                      |        | 给  |   | 返回|
                      |        | 用户|   |     |
                      |        +-----+   +-----+
                      |                      |
                      |            (未来: tool_use)
                      v
```

模型生成内容。如果 `stop_reason == "end_turn"`，则将响应返回给用户。任何其他停止原因意味着循环继续——模型被中断，需要再次迭代来完成其工作。

## 工作原理

### 1. 用户发送消息

REPL 通过 `input()` 接受输入，并将其以 `"user"` 角色消息的形式追加到对话历史中。

```python
messages.append({"role": "user", "content": user_input})
```

### 2. 代理循环将对话发送给 LLM

`agent_loop()` 函数使用完整的消息历史调用 Anthropic SDK。没有隐藏状态——模型所需的一切都在 `messages` 中。

```python
response = client.messages.create(
    model=MODEL,
    system=SYSTEM_PROMPT,
    messages=messages,
    max_tokens=4096,
)
```

### 3. LLM 以内容块响应

模型返回一个或多个内容块（通常是 `text` 块，但后续会话会添加 `tool_use` 块）。代理将整个响应追加到消息历史中。

```python
messages.append({"role": "assistant", "content": response.content})
```

### 4. 检查 stop_reason

`stop_reason` 字段告诉代理模型为何停止生成：

- **`"end_turn"`** —— 模型已完成其响应。跳出循环。
- **`"tool_use"`** —— 模型想要使用工具。（从 s02 开始处理。）
- **`"max_tokens"`** —— 模型达到了令牌限制。循环继续以让其完成。

```python
if response.stop_reason == "end_turn":
    break
```

### 5. 返回并显示

循环结束后，最终的内容块会被打印给用户。REPL 随后等待下一次用户输入。

```python
for block in content:
    if block.type == "text":
        print(block.text)
```

### 6. 重复直到用户退出

外层的 REPL 循环持续运行，直到用户输入 `q`、`quit` 或 `exit`。

## 从 s00（基线）的变化

| 组件 | 之前（基线） | 之后（s01） |
|-----------|--------------------|-------------|
| 架构 | 无代理——原始 SDK 调用 | 带 `stop_reason` 检查的 `while True` 循环 |
| 消息处理 | 无对话历史 | Messages 列表累积用户和助理的对话轮次 |

| 系统提示词 | 无 | 初始系统提示词定义代理行为 |

## 状态机的演进

`while True` + `stop_reason` 循环是最简单且最优雅的基础。随着代理变得越来越复杂——添加工具、记忆、技能、通道——这个简单的循环自然演变为一个**形式化状态机**。每个状态处理一个关注点，转换由显式事件驱动：

```
RESTORE → COMPACT → COMMAND → BUILD → RUN → SAVE → RESPOND → DONE
```

| 状态 | 作用 |
|-------|-------------|
| RESTORE | 从媒体中提取文档，恢复中断轮次的检查点 |
| COMPACT | 自动压缩过期会话，归档旧消息 |
| COMMAND | 检查斜杠命令；如果匹配则提前调度 |
| BUILD | 加载技能、记忆、历史；构建完整提示词 |
| RUN | 执行多轮 LLM 对话（工具调用 + 响应） |
| SAVE | 持久化完成的轮次，执行文件上限限制，触发合并 |
| RESPOND | 组装出站响应并交付 |
| DONE | 轮次完成 |

这种模式出现在生产级的代理框架中，其中状态机驱动整个代理循环，实现了清晰的关注点分离。每个状态是一个单一方法；转换是一张查找表。模型永远不会看到状态机——它纯粹是 harness 层面的组织模式。

你将在 s02 中看到这种演进的第一个迹象，其中 `tool_use` 成为一个分支条件。到 s07，循环将需要其第一个正式的状态分离。

## 关键设计决策

该循环刻意保持最小化。它尚未对 `tool_use` 进行分支处理——那将在 s02 中实现。它没有抽象化提供商——那将在 s03 中实现。每个会话在前一个会话的基础上只增加一种新机制。

最重要的洞察：**模型就是代理。** Harness 不决定下一步做什么。Harness 提供循环和环境；模型通过 `stop_reason` 决定何时完成。这种模式会贯穿后续每一个会话。

## 实现说明

- `repl()` 函数是外层循环（会话生命周期）。`agent_loop()` 函数是内层循环（轮次完成）。
- 消息跨轮次累积。随着时间的推移，这会造成上下文窗口压力——s06 将解决这个问题。
- 仅支持 Anthropic。SDK 是直接导入的（`from anthropic import Anthropic`）。这种耦合将在 s03 中解除。
